# Tuning Lattice — General Audit & Revision Plan

*June 2026. Produced from a four-track review (core architecture, satellite apps, UX/teaching layer, repo/process), with headline claims verified against the live site. Intended to direct revisions; file references are to the current `main` (last commit `1ad59ba`, May 21).*

---

## 1. Executive summary

Six months of piecemeal AI-assisted development produced a **feature-rich, working, genuinely shareable app** sitting on top of a structure that has reached its limit. The numbers:

| | |
|---|---|
| `src/main.js` | 32,896 lines / 1.03 MB, **997 top-level functions, 329 mutable globals, 0 classes** |
| `tuner/main.js` | 5,458 lines, monolith, copies ~33 functions from main.js |
| `overtones/main.js` | 9,263 lines, monolith, copies ~14 more |
| `index.html` | 1,905 lines — 176 buttons, 105 inputs, 14 dialogs, 13 panels |
| `src/style.css` | 4,733 lines — real token system, bypassed 178 times |
| Tests | One script that greps `main.js` for four literal source lines |
| File-format versioning | `v: 1` written everywhere, **read nowhere** |

**Verdict: neither big-bang rewrite nor incremental cleanup — a staged rebuild around an extracted core.** The app's *logic* (lattice math, HEJI spelling, projection, MPE MIDI, the tour content, the DSP in the tuner) is largely correct and salvageable. The app's *structure* (one file, globals + DOM as state, two hand-duplicated renderers, 51 mirror serialize/apply functions, eight competing keydown listeners) should not be carried forward. The strangler path is realistic here because most logic already lives in standalone functions that read globals: parameterize, move into modules, re-import. Sequence in §9.

The single most important strategic fact: **the three apps already copy-pasted the same ratio/spelling/HEJI code, and the copies have drifted** — `reduceFraction` truncates differently in the tuner than in the main app; `getNearestEtInfo` spells from different note tables; there are three independently evolving HEJI implementations. Core extraction isn't an aesthetic preference; it's stopping an active correctness divergence in the app's foundational math.

The second most important fact: **the best teaching material is written but unreachable.** The 39-step deep tour is hidden behind `<li hidden>`; the intro dialog has close handlers but nothing ever opens it; `KEYBOARD.md` (the reference for the app's signature interaction model) is published nowhere; the "Full overview" button links to a page that is never built. The UX problem is mostly *wiring and finishing*, not redesign.

## 2. What's worth keeping (port nearly as-is)

The thinking throughout is good; the assets below should survive any restructure:

- **Projection/camera math** (`worldToScreen`, `worldToCamera`) — clean and correct.
- **ET/spelling/HEJI derivation logic** — the rules are right; they just exist in triplicate.
- **The AudioWorklet processors** (`karplus-worklet.js`, `modal-resonator-worklet.js`) and `custom-oscillators.js` — clean, self-contained, keep verbatim.
- **`src/tour-steps.js`** — declarative step data with a documented schema, separated from its runner. *This is the pattern the rest of the app should follow.*
- **The tuner's DSP core** — AMDF autocorrelation with parabolic interpolation, voiced/unvoiced hysteresis, octave-error gating, confidence-weighted smoothing, plus an in-browser calibration workbench. The best-engineered code in the repo.
- **URL-state shareability** — full state in the hash, share popover, JSON save/load, Scale Workshop handoff, `?embed` mode. Best-in-class for the genre.
- **The token/theme system's bones** — ~80 CSS custom properties, five complete themes.
- **The Tuning the Ear deck** — manifest-driven, per-slide interaction locks, intro card, escape hatches into the editor/tuner. The most progressive-disclosure-correct experience in the codebase, better than the main app's own onboarding.
- **`INTRODUCTION.md`** — the "seven ways to use it" framing is the correct information architecture for the whole product (see §6).
- **The preset state vocabulary** — the ~45 key names are a decent de facto schema to formalize.
- **Deploy pipeline** — GitHub Actions → Vite multi-page build → Pages. Correct and modern.

## 3. Verified defects (fix regardless of any larger plan)

Confirmed directly, not just agent-reported:

1. **`#intro-dialog` can never open.** `src/main.js:31535–31548` binds only close/dismiss handlers; no `showModal()` call exists for it. Its content ("Take the tour" / "Full overview") is unreachable.
2. **`presentation.html` is never deployed.** It's tracked but absent from `vite.config.js` build inputs. The live site serves the app shell with HTTP 200 for *any* unknown URL (404-fallback), so the "Full overview" link (`index.html:1561`) silently reloads the app. The page itself is still a wireframe (placeholder video slots, CTA href="#").
3. **The 39-step Deep Tour is hidden** behind `<li hidden>` (`index.html:1583`) — ~75% of authored teaching content unreachable.
4. **Tour copy has drifted from the UI:** deep tour says "Options > Analysis ▸ Show Microtonal" but the control is the View panel's "Interval Overlay" (`index.html:1500`); tour says "`]` clears the loop," `INTRODUCTION.md:152` says "`[`".
5. **Core math has forked across apps:** `reduceFraction` uses `Math.trunc` division in `tuner/main.js:804` vs plain division in `src/main.js`; `getNearestEtInfo` indexes `noteNamesSharp` (tuner) vs mixed `noteNames` (main) — same ratio can spell differently across apps; three diverged HEJI annotation implementations.
6. **No CI quality gate:** `deploy.yml` builds and publishes without running `npm run check:regression`. A red smoke check still deploys.
7. **Dead code tracked despite `.gitignore`:** `tour.js` and `tour-quick.js` (byte-identical), `tour-deep.js` (empty), `deep-tour-draft.js` — all superseded by `src/tour-steps.js`, all still tracked because they were committed before being ignored. Also: two tracked `.DS_Store`s, empty `NOTES.md`, committed Claude session memory under `.claude/projects/`, a stale root `CNAME` contradicting `public/CNAME`.
8. **319 MB of Python venvs** (`.venv/`, `.venv311/`) in a JS project, unignored (excluded only by Python's self-ignore).
9. **`npm audit`: 1 high + 3 moderate**, all dev-chain (esbuild dev-server exposure, rollup). Vite is 5.x; current is 8. Nothing affects the deployed static site, but local `npm run dev` while browsing is a real exposure.
10. **Dead branches shipped:** `getNodeRadius` returns 35 in both branches; `shouldDisableLayoutScale()` unconditionally returns `false` yet its result is threaded through dozens of signatures including the entire SVG exporter.

*(False alarm worth recording: slide 14 of the Tuning the Ear deck is NOT missing in production — Vite inlines `14-syntonic-major-7.json` as a base64 data URI because it's under the inline threshold.)*

## 4. Architecture assessment — `src/main.js`

### 4.1 State: globals plus the DOM itself
No store of any kind. ~329 mutable module globals, including a held-key flag forest (`rHeld`, `tHeld`, `lHeld`, `vHeld`, …, main.js:520–527) and ~20 interacting `*Mode` booleans. Core tuning parameters live **in the DOM**: `buildLattice()` reads `Number(fundamentalInput.value) || 220` (main.js:6634); serialization reads inputs directly (main.js:24818). The model cannot exist without the page — which is also why nothing is unit-testable.

Change propagation is manual: **158 scattered `draw()` calls and 123 `schedulePresetUrlUpdate()` calls** are the de facto reactivity system. Forgetting one after a mutation is this codebase's signature bug class (the git history's "serialization bugs fixed" commits corroborate).

### 4.2 Data model: doubly-represented, float-fragile
Nodes are ad-hoc literals mixing model, grid addressing, presentation, derived acoustics, and UI/audio state in ~18 fields. Every node carries *both* prime exponents and a reduced num/den, synced by hand. Ratio arithmetic goes through `Math.pow` into JS doubles (main.js:8007–8030) — beyond ~2^53, exactness silently dies, and exactness is the one thing a JI app must never lose. Custom nodes use magic id base 200000 with a comment admitting references "silently break" otherwise (main.js:26463). Edge/triangle/snapshot identity rides on at least four parallel string-key conventions.

### 4.3 Rendering: a 988-line `draw()` plus a complete second renderer
Canvas 2D immediate-mode, event-driven full redraws (fine for this node count). The problem: **SVG export is an entire parallel renderer** — `buildLayoutSvgString` (main.js:27446, 1,361 lines) re-implements edge trimming, label placement, triangles, guides, and HEJI composition. ~2,000 duplicated lines; every visual change must be made twice and divergence is guaranteed ("fix distance label spacing in PDF"). HEJI text composition and text measurement are each duplicated canvas/SVG. PDF export is `window.open` + `document.write(svg)` + `print()` with a hardcoded font-load wait list.

### 4.4 Serialization: 51 mirror functions, versioning in name only
One state shape serves URLs, files, presets, snapshots. `v: 1` is written but **never branched on**; loading deep-merges incoming state over current defaults — tolerant of missing keys, silent on renames/restructures (old field ignored → data loss without error), and unable to detect "file newer than app." Save and load are duplicated field-by-field across ~25 `serialize*`/`apply*` mirror pairs; the apply side is a hand-sequenced pipeline whose ordering constraints live in comments. The canonical preset library (`src/presets.json`) stores **LZ-compressed URL blobs** via a ~200-line vendored LZ-string — unreadable, undiffable, hostage to decoder compatibility. The snapshot-set format already changed once ("diff compression") *without* a version bump and with no migration code retained.

### 4.5 Audio and input
`startVoice` (236 lines) is a conditional ladder over four synthesis backends — a textbook strategy-pattern refactor, with MPE MIDI-out channel allocation interleaved into the same global voice list. The worklets themselves are clean. Input: **eight separate `window` keydown listeners** with load-order-dependent interactions; pointer handling is three giant mode-branching functions (653/521/364 lines).

## 5. The three-monolith problem

`vite.config.js` already builds everything from one root, and `overtones/main.js` proves relative imports from `src/` work (it imports `custom-oscillators` and `interval-names.json`). Yet tuner and overtones each re-implement the ratio/spelling/HEJI/theme stack:

- main ∩ tuner: **33 identical-name functions** + copied data tables (`TRUE_SPELLING_INTERVALS`, `HEJI_RULES`, note arrays, prime colors)
- main ∩ overtones: 14; tuner ∩ overtones: 18
- CSS: tuner (1,030 lines) and overtones (609) redeclare the same theme tokens and `@font-face`
- `analyzeRatioForTrueSpelling` is still byte-identical between tuner and overtones — **consolidation is cheap now and gets more expensive every month**

Also in the satellites: the tuner ships its ~1,200-line calibration workbench (a dev tool) to every user; `tuner/mobile/` is a second hand-maintained HTML tree (~80 element IDs) that must stay in sync with the desktop one; the Tuning the Ear import script hardcodes an absolute Dropbox path and warns rather than fails on collisions.

## 6. UX, design, and the teaching layer

### What the audit found
- **The interaction model is the product's soul and is invisible.** Twelve-plus hold-key quasimodes (Blender/Vim-grade expert design, right for performing composers) — discoverable only via a 15-line static cheat-sheet overlay and 21 tooltips. No `?` overlay, no command palette, no pressed-key HUD, and `KEYBOARD.md` is unpublished.
- **Onboarding funnel leaks at every joint.** Welcome overlay → 12-step quick tour (well designed) → then a cliff: 13 panels, 176 buttons, no intermediate path (the hidden deep tour was exactly that path). Users arriving via shared URL get *no* onboarding at all. Zero contextual help links anywhere in the app.
- **Markup is hand-grown with paste seams:** the same 11-font dropdown copy-pasted **9 times** (index.html:632–900); View-panel "Show" options duplicated wholesale in the Layout panel with parallel id schemes.
- **The design system is proto, not broken:** good tokens and five themes, but a redundant alias layer (`--ink` vs `--chrome-ink`), 178 hex literals bypassing tokens (the intro dialog hardcodes the accent color and wouldn't theme), no type/spacing/radius scales (49× `12px`, 6× `9px` — below legible), an ad-hoc z-index ladder of 18 values, and the palette forked by copy-paste into `docs/style.css` and `presentation.html` (already drifted).
- **Docs are forked:** `INTRODUCTION.md` was hand-converted to `docs/index.html` and the two have already reworded differently. The docs page has no screenshots (for a visual tool), no link back to the app, no keyboard reference.
- **Mobile:** the main app has none ("touch" appears once in 33k lines — in a comment). The asymmetry matters because **book readers will open Tuning the Ear links on phones**; the deck's tap-to-play would mostly work if pointer events were handled.
- **Accessibility:** good bones (native `<dialog>`, aria-expanded, visually-hidden labels, focusable canvas) but: no keyboard path to add/remove/play a node, ~10 `outline:none` without `:focus-visible` replacement in older panels, zero `prefers-reduced-motion`, near-flat heading/landmark structure.

### The redesign direction (when the structural work permits)
`INTRODUCTION.md`'s "ways to use it" is the correct IA; the chrome organizes by implementation history instead. Reorganize the surface around modes — **Build / See / Play / Compose / Publish / Practice** — with panels existing only within their mode. That converts the 176-control cliff into progressive disclosure (~30 controls visible at a time). First-five-minutes target: land on a *sounding* default (hear before learn); welcome overlay with three doors — "Learn the lattice" (tour), "I read Tuning the Ear" (deck), "I know what I'm doing" (explore + `?` overlay); one-at-a-time contextual hints replacing the static cheat block; deep tour resurfaced as per-topic mini-tours (Layout, Snapshots, MIDI, Looper).

## 7. Engineering process

- **Testing:** the smoke script asserts four literal source lines still exist in main.js — a hand-rolled tripwire against AI agents re-deleting past fixes. It fails on legitimate refactors and passes on real regressions. The 13-step manual checklist shows the invariants are *known*, just not automated. Nothing covers audio, tours, presets, export fidelity, themes, or the deck.
- **No `CLAUDE.md`/`AGENTS.md`** — for a project built with AI agents, the most surprising gap. The grep-guards are a brittle substitute for stating invariants in prose + tests. The 1MB main.js is itself an AI hazard: beyond a single read window, it forces blind partial edits — the root cause of the regressions the guards exist to catch.
- **Git:** 139 commits, single author, main-only, terse messages, many-concerns-per-commit. 43.7 MB all-loose objects (never gc'd); ~35 MB of historical `node_modules`/`dist`; 110 historical copies of main.js. `git gc --aggressive` fixes most of it.
- **Dependencies:** all three runtime deps genuinely used. Vite 5→8 is likely a one-hour change here (tiny config surface) once fixture tests exist. No linter, formatter, or test runner installed.

## 8. Target architecture

Four-layer decomposition, TypeScript, ~10–12k lines replacing 33k (full module-by-module sketch with line budgets is in the architecture appendix below):

```
core/      pure, zero DOM — shared by lattice, tuner, overtones
           monzo.ts (prime-exponent vectors + bigint fractions — exact arithmetic)
           pitch.ts (ET mapping, spelling, HEJI), lattice.ts (axes → graph),
           intervals.ts (name/comma lookup)

state/     one store; slices (tuning, scene, view, layout, synth, play, ui);
           ONE subscription → schedule draw + URL update   ← deletes the
           158-draw()/123-schedulePresetUrlUpdate bug class outright

render/    scene-builder.ts: (state) → DisplayList — geometry, trimming,
           label placement computed ONCE
           canvas.ts and svg.ts each consume the DisplayList   ← kills the
           2,000-line dual renderer; hit-testing and future targets come free

io/        versioned, validated schema; migrate(vN → vN+1) chain kept forever;
           presets.json as plain readable state docs; lz-string from npm

audio/     VoiceBackend interface (oscillator | soundfont | karplus | resonator);
           midi-out-mpe isolated; worklets unchanged

input/     ONE keydown/keyup pipeline with a declarative mode-scoped binding
           table; pointer state machine hit-testing against the DisplayList

ui/        per-panel controllers mirroring index.html sections; repeated markup
           (9× font dropdowns, duplicated Show toggles) generated from data
```

Tests where they're cheapest and matter most: **property tests on monzo math, round-trip tests on serialization (seeded with the 40+ Dropbox Creator exports as fixtures), golden-file snapshots of scene-builder/SVG output.** The manual checklist shrinks to what WebAudio genuinely resists automating.

## 9. Phased revision plan

Each phase ships independently; order matters (the safety net precedes the surgery).

### Phase 0 — Stop the bleeding (a day)
Zero-risk, immediate user value:
1. Wire `#intro-dialog` open (or delete it); fix or remove the `presentation.html` link.
2. Un-hide the deep tour; fix the two tour-copy drifts (§3.4).
3. Hygiene commit: `git rm --cached` dead tour files, `.DS_Store`s, `NOTES.md`, `.claude/projects/`; delete root `CNAME`; move `name-conflicts.txt` + `backup/intervals_names_gann.json` to `docs/data-sources/`; fix `.gitignore` (`.venv*/`, `.claude/`); delete the venvs (frees 319 MB).
4. Add `npm run check:regression` to `deploy.yml` before publish.
5. Delete dead branches (`shouldDisableLayoutScale` plumbing, `getNodeRadius`), debug `console.log`s, `window.snapshotDebug`.
6. Write `CLAUDE.md`: serialization compatibility contract, build map, the four guarded invariants and why, repo rules, "main.js may not grow" budget.

### Phase 1 — Safety net (a week)
1. Check the Dropbox Creator exports into `fixtures/` (plus snapshot-sets, deck diagrams, every presets.json URI).
2. Extract serialization functions from main.js into an importable module — the first incision, small and mechanical.
3. Vitest: decode → normalize → re-encode → decode lossless, for every fixture. **This is the gate everything later must pass.**
4. Add vitest + a formatter (prettier) + minimal eslint; CI runs all of it on push.
5. Upgrade Vite (clears the audit findings) once fixtures are green.

### Phase 2 — Extract the shared core (1–2 weeks)
1. `src/lib/` (or `core/`): ratio math, spelling, HEJI, interval lookup — **monzo + bigint**, property-tested. Resolve the three drift cases as explicit decisions (which `reduceFraction`, which note table).
2. Import from all three apps; delete the copies. Do tuner↔overtones first while `analyzeRatioForTrueSpelling` is still byte-identical.
3. One shared `theme.css` token sheet imported by all five surfaces (app, docs, tuner, overtones, presentation); delete the alias layer; add type/spacing/z-index scales.
4. Split the tuner's calibration workbench out of the user bundle.

### Phase 3 — One scene, two renderers (2–3 weeks; the single highest-leverage refactor)
1. Build `scene-builder` producing a DisplayList from current globals (strangler-style — the store can come later).
2. Port canvas `draw()` to consume it; golden-snapshot the DisplayList.
3. Port SVG export to consume it; golden-snapshot the SVG. Delete ~2,000 duplicate lines.
4. Unify HEJI composition/measurement to single implementations.
5. Re-point hit-testing at the DisplayList.

### Phase 4 — State, format, input (2–3 weeks)
1. Introduce the store; migrate globals slice-by-slice; one subscription replaces all manual `draw()`/URL calls.
2. Versioned schema + first real migration; honor `v` on load; convert `presets.json` to plain state docs; vendored LZ-string → npm package.
3. Collapse snapshot duplication (numeric + letter slots = one slot type; "state doc + performance overlay").
4. One keyboard pipeline with a declarative binding table; pointer state machine. `startVoice` → `VoiceBackend` strategy.

### Phase 5 — UX finish (2–3 weeks, parallelizable with 4)
1. Publish `KEYBOARD.md`; hold-`?` keyboard overlay in-app.
2. Contextual one-at-a-time hints; sounding first-run default; three-door welcome.
3. Generate `/docs/` from the markdown sources; screenshots + `?embed` live examples; interlink app dialogs ↔ docs anchors.
4. Generate the 9× font dropdowns and duplicated Show toggles from data.
5. Touch support for the Tuning the Ear deck path (tap-to-play, viewport sizing, TOC drawer) — not the whole editor.
6. Accessibility pass: `:focus-visible` everywhere, `prefers-reduced-motion`, keyboard node add/remove/play, landmarks.

### Phase 6 — The IA redesign (when 2–4 are done)
Mode-based chrome (Build / See / Play / Compose / Publish / Practice), panels scoped to modes, progressive disclosure. Deepest change; the feature set is stable enough to know the right shape, but it should land on the new architecture, not the old one.

## 10. Rebuild vs. refactor, per subsystem

| Subsystem | Call | Why |
|---|---|---|
| Ratio/pitch/HEJI math | **Extract + harden** (bigint) | Logic right, representation fragile, copies drifting |
| Projection/camera | **Keep** | Already clean |
| Canvas + SVG renderers | **Rewrite** into scene-builder + 2 thin targets | The 2,000-line duplication is unsalvageable as-is |
| Serialization | **Rewrite** schema-driven; keep the key vocabulary | 51 mirror functions, versioning is fiction |
| Audio engine | **Refactor** to VoiceBackend strategy | Works; structure is one interface away |
| Worklets, oscillators | **Keep verbatim** | Clean |
| MIDI (in / MPE out) | **Keep logic, isolate module** | Correct, just interleaved |
| Keyboard/pointer input | **Rewrite** declaratively | 8 listeners + flag forest breeds mode bugs |
| Snapshots/looper/pattern | **Refactor** on new store | Duplicated slot types, salvageable logic |
| Tuner DSP + calibration | **Keep**, split workbench out | Best code in repo |
| Overtones app | **Refactor** onto shared core | Already half-integrated |
| index.html / panels | **Regenerate** repeated markup; later mode-IA | Paste-grown |
| CSS | **Consolidate** tokens, keep themes | Proto design system worth finishing |
| Tours/teaching content | **Keep content, fix wiring** | Material is good and hidden |
| Tuning the Ear pipeline | **Keep**, de-hardcode path, add manifest→asset build check | Sound design, brittle edges |

## 11. Capability opportunities (post-revision)

Unlocked cheaply by the new architecture, roughly ordered by value-for-effort:

1. **Deck-on-phones** — the book audience's actual arrival context (Phase 5.5).
2. **Command palette** (⌘K) over the declarative binding table — discoverability for the quasimode model falls out of Phase 4.4 nearly free.
3. **Exact deep lattices** — bigint core removes the silent 2^53 ceiling on higher-prime/deep structures.
4. **New export targets** (PNG at resolution, animated SVG, video frames) — each is one more DisplayList consumer.
5. **Readable, diffable, shareable presets** — plain-JSON presets enable community preset contribution via PRs.
6. **MTS-ESP / Scala `.scl`/`.kbm` export** — small once the core is a module (Scale Workshop handoff already exists).
7. **Undo everywhere** — generic store-snapshot undo replaces the layout-only undo.
8. **Embeddable lattice widget** — `?embed` + the extracted core ⇒ a `<script>` one-liner for blog posts and the book's web edition.
9. **Test-backed AI development** — with fixtures, property tests, and CLAUDE.md, agent-driven feature work stops needing grep tripwires.
